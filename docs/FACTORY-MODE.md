# Factory mode — plan (2026-10-11, for review before implementation)

Scope: what happens to every board between "flashed for the first time" and "in the box", on
both sides (firmware + portal), and what the assembly station runs. Nothing here is built yet
except the pieces marked *exists*.

## 1. What exists today

| Piece | State |
|---|---|
| Gauge bring-up (LiFePO4 config, current-sense calibration, LED-guided) | *exists*: runs once per board on first boot, `bringup_v1` NVS flag (FACTORY_BRINGUP.md) |
| Device identity | *exists*: hub uuid = eFuse MAC as decimal (`hubid` console command) |
| Hub row in the portal | admin creates it by hand (Admin → Hubs, needs a `devices` model row) |
| Token | `GET /api/hubs/{uuid}/token`, unauthenticated, works only for hubs without a secret; `POST …/token` + `X-Hub-Secret` for hubs enrolled with `php artisan hub:secret {uuid}` (*exists*, nothing in the field uses it) |
| Firmware token fetch | GET only (RequestManager::getJWTToken) |
| Factory reset | `ConfigManager::factoryReset()` erases **all** of NVS (`nvs_flash_erase`) |
| BLE provisioning | IDF provisioning manager, security 1, PoP = `ConfigManager::getProvisioningPin()` (same value on every device today) |
| Console self-tests | `battery`, `sdbench`, `nfcdiag`, `ledon`, `play`, `speedtest`, `pdstatus`, `efusemac` … (operator-driven, no pass/fail) |

## 2. Goals

1. **Every board gets exercised** before it is boxed: LED, buttons, NFC reader + pogo/reed,
   SD card, speaker (and jack), charger + gauge (incl. the existing bring-up), WiFi, BLE
   advertising, PD contract. Pass/fail recorded per board.
2. **Every board is enrolled**: hub row created in the portal with hardware revision, serial
   number, batch, firmware version and the test report; a per-device secret generated by the
   portal and written to the device; the device proves it can fetch a token with it.
3. **Nothing an operator can forget**: one station script drives flashing, tests, enrollment,
   cleanup and the label; the device cannot leave the station "half done" without the LED
   showing red.
4. **Field-safe**: a factory reset (console, future button combo) keeps the enrollment; a
   re-flash keeps it; the gauge bring-up is not repeated on re-flash.

## 3. Device side (firmware)

### 3.1 Factory test mode (`ft …` console protocol)

Entered only over the USB console (physical access = authorisation). Normal operation stays
untouched; the mode is a set of commands that take the subsystems over one at a time and
answer with one JSON line each (`FT {...}`) so the station can parse them.

| Command | What the firmware does | Pass criterion (automatic unless noted) |
|---|---|---|
| `ft begin` | stops sleep/OTA/scenes, answers identity: uuid, eFuse MAC, fw version+code, hw rev, reset reason, bring-up flag | — |
| `ft power` | VBUS, PD contract (CH224Q), charger state/faults, gauge chem id, cell V, temp, FCC, SOC, `bringup_v1` | VBUS 4.6–5.5 V (or PD 9 V if requested), gauge responds, chem id 0x418, no faults, bring-up done |
| `ft sd` | mount, CID serial, free space, 1 MB write + read-back + sha | mounted, read-back ok, write ≥ 0.5 MB/s (threshold to confirm; the bench Powerway card does 0.3) |
| `ft led <r|g|b|w|off|cycle>` | drives all 5 LEDs | operator confirms colours on the station UI |
| `ft buttons <s>` | reports every press (which button, ms) for s seconds | all 4 buttons seen (station prompts one at a time) |
| `ft nfc <s>` | reader IC version, waits for a tag, reports UID; pogo/reed level | reader found, test tag read within s seconds, pogo level changes with the figure |
| `ft audio spk` | 1 kHz tone 2 s on the speaker; reports IBAT/VSYS current delta during the tone | current rises by ≥ 60 mA (speaker is driven) + operator hears it |
| `ft audio jack` | same tone with the operator's headphones plugged | operator confirms (jack switching is mechanical, no detect pin) |
| `ft wifi <ssid> <pass>` | scan (RSSI of the factory AP), connect, IP | connected within 15 s, RSSI > −70 dBm |
| `ft ble` | starts BLE advertising for 10 s | station sees the advertisement (or operator's phone) |
| `ft enroll <secret> <serial> <hwrev>` | writes NVS namespace `factory`: `hub_secret`, `serial`, `hw_rev`, `enrolled_at` | written and read back |
| `ft cloud` | `POST /api/hubs/{uuid}/token` with the stored secret, then `GET …/validate-token` | both 200 |
| `ft wificlear` | erases WiFi credentials (so the customer's BLE provisioning runs) | provisioning manager reports not provisioned |
| `ft done <pass|fail> <report-sha>` | stores `ft_result`, `ft_at`, report hash; LED solid green (pass) / pulsing red (fail); restarts | — |
| `ft info` | dumps the `factory` namespace (secret masked) | — |

Rules: `ft` commands are refused unless `ft begin` ran in this boot; a board whose
`ft_result` is not `pass` boots normally but blinks red twice at power-on (so a skipped board
is noticed at packing); `ft begin` is the only way to clear a fail.

### 3.2 Enrollment data at rest

- NVS namespace `factory` (new). `ConfigManager::factoryReset()` changes from
  `nvs_flash_erase()` to erasing the app namespaces one by one (`tilkie`, `requestmgr`,
  WiFi, OTA keys) and leaves `factory` alone. A full flash erase with esptool still wipes it
  — acceptable, that is a service operation and the station can re-enroll.
- Alternative for discussion: eFuse user block (BLOCK3, 32 bytes, write-once). Survives
  everything, cannot be rotated. Recommendation: NVS now, eFuse only if we ever need
  tamper-evidence.
- Secrets are stored in the clear (no flash encryption on this product). What a stolen secret
  gives: a token for that one hub. Acceptable for v1; flash encryption is a separate project.

### 3.3 Token fetch

`RequestManager::getJWTToken()`: if `factory/hub_secret` exists → `POST /hubs/{uuid}/token`
with `X-Hub-Secret`; otherwise the legacy GET (keeps the bench board and the existing dev
units working). Once every shipped unit is enrolled, the backend turns the GET off.

### 3.4 BLE provisioning PoP

Today every device uses the same PoP, so anyone within BLE range can provision (and thereby
own the WiFi credentials of) a toy that is in provisioning mode. The station should write a
per-device PoP into the `factory` namespace and print it in the label QR together with the
uuid. The app reads uuid + PoP from the QR; the existing `qr` console output already has the
ESP provisioning payload format. **Needs the app developer** (small change: parse the QR).

## 4. Portal side

- Migration: `hubs.serial_number` (unique, nullable), `hubs.batch`, `hubs.enrolled_at`,
  `hubs.factory_passed_at`, `hubs.factory_report` (json). `devices` row = product model
  (today the rows are faker names; create "TilkieTalkie Adem v7" and point the station at its id).
- `HubEnrollment` service: `enroll(uuid, deviceId, hwRev, serial, batch, fwVersion)` →
  creates or updates the hub, generates the 32-byte secret, stores the bcrypt hash, returns the
  plaintext once. Re-enrolling rotates the secret (the previous one is dead; fine on the station,
  the board is not shipped yet). `hub:secret` keeps using the same service.
- `POST /api/factory/hubs` (auth: a dedicated Sanctum token with ability `factory:enroll`,
  created for the station user; rate-limited; logged) → `{uuid, secret, serial}`.
  `POST /api/factory/hubs/{uuid}/report` → stores the test report + pass/fail.
  `GET /api/factory/hubs/{uuid}` → status (for a re-run).
- Admin page "Factory": list of enrolled hubs with serial, batch, pass/fail, firmware, enrolled
  at; detail shows the report; CSV export per batch. Binding to a customer stays as it is
  (`POST /api/hubs/{hub}/bind` from the app).
- Later (not v1): device-scoped token instead of the owner's Sanctum token (SECURITY-CHANGES.md).

## 5. Station (tools/factory/station.py)

Python, pyserial + requests, runs on the Mac at the bench or a Raspberry Pi at the line.

1. Operator scans/enters the batch; the script allocates the next serial
   (`<batch>-<nnnn>`, format to confirm).
2. `esptool write_flash` the release image (bootloader + partitions + app), wait for boot.
3. Gauge bring-up: wait for green (poll `battery` / `ft power` until `bringup_v1`), with the
   FACTORY_BRINGUP.md timeouts.
4. `ft begin` → `ft power` → `ft sd` → `ft led cycle` (operator confirm) → `ft buttons 20`
   (prompt each) → `ft nfc 15` (operator taps the test figure) → `ft audio spk` →
   `ft audio jack` (operator) → `ft wifi <factory AP>` → `ft ble`.
5. Enroll: `POST /api/factory/hubs` → `ft enroll <secret> <serial> <hwrev>` → `ft cloud`.
6. `ft wificlear` → `ft done pass <sha>` → `POST …/report`.
7. Label: QR payload `{uuid, pop, serial}` as PNG (printer integration later); the script also
   writes `factory-logs/<serial>.json`.
8. Any failure: `ft done fail`, report posted, board goes to the rework bin with the log.

Expected time per board: ~2 minutes plus bring-up (under a minute on USB).

## 6. Open decisions (owner)

1. Secret at rest: NVS `factory` namespace (recommended) or eFuse BLOCK3 (permanent).
2. Station auth: one Sanctum token with `factory:enroll` for a "factory" user (recommended)
   vs. per-operator logins.
3. Serial number format and whether it is printed on the PCB label, the box, or both.
4. Per-device BLE PoP in the label QR (recommended; needs a small app change) or keep the
   shared PoP for the first batch.
5. SD write-speed threshold (depends on the card you ship; the bench card would fail 0.5 MB/s).
6. Does the station need a label printer in v1, or is the QR printed elsewhere from the CSV.
7. Keep the legacy unauthenticated token GET until all dev units are enrolled, then disable.

## 7. Order of work and estimate

1. Firmware: `factory` namespace + factory-reset change + token POST (½ day) — ship-safe
   on its own, can go into 1.2.x.
2. Firmware: `ft` protocol (1 day), LED red-blink for untested boards.
3. Portal: migration, service, factory API, admin page (½–1 day).
4. Station script + dry run on the bench board, then on 3–5 boards of the first batch (1 day).
5. App: QR with PoP (app developer, when ready).
