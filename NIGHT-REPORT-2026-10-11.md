Flow verified end to end on the bench: `ota check` → backend offers release → device downloads 2.27 MB in ~15 s into the spare app partition, SHA-256 verified, status posted (downloading/applying), reboot, new image confirms itself (rollback cancelled) once Reverb connects, `success` posted with the new version_code; hub row shows 1.1.1. Version comes from `CONFIG_APP_PROJECT_VER` in sdkconfig (single source, the backend parses it from the .bin). Console: `ota`, `ota check [release]`, `ota url <url> <sha256> <size>`, `version`. Remote command `ota-update <release_id>`; the admin Hub page has "Send update command" and release pinning; updates only start when idle (no playback/figure/download, charging or ≥40 %) — mandatory ones force after 1 h.
- Backend security branch `feature/hardening` (merged on the bench, not pushed): hub secret enrollment (`php artisan hub:secret`), POST token with X-Hub-Secret, server-side `POST /api/hubs/{hub}/command` (allowlist in config/tilkie.php), dual publish on `private-device.{uuid}`, X-Client-Source bypass removed, rate limits, appScheme XSS fix, Horizon gate. docs/SECURITY-CHANGES.md explains the mobile-app migration.

- OTA safety, learned the hard way: my first crash-test image confirmed itself the moment Reverb connected and then crashed, so the bootloader could not roll it back and the board crash-looped until I reflashed it over USB. Fixed in two layers: (1) a new image is only confirmed after 60 s of uptime (any reset before that → bootloader rollback), (2) a crash-loop guard in RTC memory: three crash resets in a row without 5 min of stable uptime switch the boot partition back to the previous firmware and report `rolled_back`. Both paths are exercised below.
