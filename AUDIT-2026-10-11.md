Loop task stack: 16 KB, **13.4 KB used (82 %)**. Almost nothing lives in PSRAM; TLS, WiFi buffers, JSON, Strings and download buffers all compete for ~50 KB of internal RAM.

**Download test (10 MB plain-HTTP file): crashed and rebooted on every attempt (4/4).** Sequence each time: SD writer falls behind the network (`Buffer swap delayed`, then `Write task blocked - timeout waiting for previous write`), the download aborts, then `assert failed: xQueueGenericSend queue.c:936 (pxQueue)` → panic → reboot (`rst:0xc RTC_SW_CPU_RST`). Because the queue persists on SD, the device re-attempted on every boot (crash loop) until the queue entry was removed. Download stats afterwards still read "7 successful, 0 failed". The 6 earlier real downloads (924 KB total, ≤~150 KB each) had succeeded, so the failure is size/speed dependent.

**Also observed in that test:** the serial handler lower-cases the whole command line (URLs included), and a 146-byte server error/redirect page was saved and reported as a completed download because the HTTP status line is never checked.

**Playback test (cached 157 KB MP3):** play, pause (wall-clock position), byte-estimate resume, natural end all worked. Internal free heap fell 50.6 → 36.7 KB while playing; minimum free heap dropped to **7.6 KB**. Volume was at **100 %** with no ceiling applied (restored to 100 % after the test).

## 2. Why the device "cannot handle the load"

It is not CPU. Core 0 carries WiFi/BT; core 1 runs one cooperative `loop()` at priority 1 that performs, synchronously: HTTP + JSON on every figure tap, SHA-256 of every cached track on every tap and every 5 minutes, bit-banged battery I2C with busy-waits (~40 register reads/s, estimate ~100 ms/s plus 50–300 ms spikes every 5 s), NVS writes on every volume step, TLS handshakes for Reverb inside the WebSocket callback, 5–30 s WiFi waits, and unbounded `while(!Serial.available())` loops. The audio task sits at the same priority on the same core behind the same recursive mutex. So any long call freezes buttons, LED, NFC detach, battery cutoff and sleep, and starves the decoder.

Task inventory today: loopTask (c1,p1), AudioPlayback (c1,p1), SDWriteTask per download (c1,p1, log says c0), async_tcp (c0,**p23** = WiFi priority), wifi (c0,p23), arduino_events (c1,p19), tcpip (unpinned,p18). No NFC, battery, network or UI tasks exist.

Internal RAM is the second constraint: `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC` (TLS in internal RAM), `SPIRAM_MALLOC_ALWAYSINTERNAL=16384` (every allocation ≤16 KB goes internal first), static WiFi TX buffers, and 2×32 KB download buffers allocated forever at boot. Reverb's subscribe does a second TLS session on top of the WebSocket's, which matches the 10 KB minimum-free reading.

## 3. Firmware findings by subsystem (critical + high; details in the per-agent reports)

### 3.1 Downloads & SD (`src/FileManager.cpp`, 2057 lines)
- **C — Crash on every sustained download** (reproduced). Writer task torn down on a 200 ms timer, semaphores deleted while in use (`:1979-1999`, `:1678-1682`); AsyncClient deleted inside its own callbacks (`:2009-2013`) → re-entrant double cleanup; `downloadInProgress=false` set before the nested cleanup finishes, so the next download's state gets torn down too.
- **C — No HTTP status check** (`:1560-1621`): 301/404/500 bodies saved as `.mp3` and reported success; then the 5-minute re-hash deletes and re-queues them forever.
- **C — Data races across cores** on `downloadQueue`, `requiredFiles`, `activeDownloads`, `pendingCompletions` and the JSON files (no locks, `CONFIG_FATFS_FS_LOCK=0`).
- **C — SHA-256 of every present asset on every tap and every 5 min, on loopTask**, 512-byte reads (`:942-975`, `RequestManager.cpp:434-441`, `:365-369`). ~1 s/MB → tens of seconds to minutes of freeze.
- **C — No checksum at download time**; `asyncState.checksum` is reused to carry the URL path (`:719`).
- **H — Backpressure by 100 ms timeout** (`:1898`, `:1542`): writer at priority 1 competes with loop + audio; a normal SD busy period aborts the download. The 10 Mbit/s "ceiling" is the 64 KB TCP window without scaling, not AsyncTCP.
- **H — `pingGoogle` connectivity probe blocks loop 10–15 s per queued task** when WAN is down (`:306-347`, `:758`); sleep is refused while the queue is non-empty, so an offline device never sleeps.
- **H — Persistence is truncate-then-write** (queue, required files, manifests); power loss empties the lists; temp files never synced.
- **H — Sleep cuts SD power without unmount** (`SleepController.cpp:146-165`).
- **H — Free-space check truncated to 32 bit** (`:992-997`), no eviction, no LRU.
- **H — Audio and downloads share the FATFS volume lock**; a 32 KB write (59 ms measured) exceeds the ~20 ms I2S DMA margin.
- M: tail-fetch "repair" is unsafe; chunked encoding unsupported; `deleteFigureFiles` targets the old `/figures/` layout; `cleanupTempFiles` scans the wrong directory; `formatSDCard` is a recursive delete with no confirmation; `isChargingRequired()` exists but is never called (downloads run on battery); 2×32 KB internal buffers never freed although 8 MB PSRAM is idle.

### 3.2 API client & figure flow (`src/RequestManager.cpp`, 1058 lines)
- **C — https→http downgrade for API and media** (`:62-66`, `:112-114`, `FileManager.cpp:574-577`): the owner-user bearer token travels in cleartext on every call; the manifest can be tampered with (arbitrary SD paths via unvalidated `storage_path`, arbitrary audio URLs). The CA bundle is already compiled in (`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y`) and unused.
- **C — Shared vectors mutated from the async_tcp task** (heap corruption risk).
- **C — Online path never falls back to the cached manifest** on DNS/5xx/401/parse failure: a figure that is fully cached plays nothing when the portal is down but WiFi is up.
- **H — Token lifecycle**: any transient error on `validate-token` rotates the token (which revokes the user's other device server-side); a 401 at runtime is never handled; Reverb keeps the stale token.
- **H — Download-complete callback only registered if WiFi is up within 5 s of boot** (`main.cpp:941-958`); otherwise downloads finish but never trigger playback.
- **H — First transient failure of any track fails the whole figure**; nothing plays until every track is present; shared assets between figures stall the second tracker.
- **H — Unbounded JSON**: `MAX_RESPONSE_SIZE` unused, full body printed to serial (incl. token), ~0.9 KB per track, no filter → internal heap drain on large figures.
- **H — `factoryReset` erases the whole NVS partition**, including `bringup_v1`, so a reset re-runs gauge provisioning/calibration (needs USB charge current, technician flow). Same erase in `ConfigManager()` on NVS-full.
- M: `manifest_checksum` parsed but never compared (no etag/304); `pending_manifests` two-phase commit never read at boot; duplicate storage of the same track under two contents; custom tracks in m4a/ogg/wav are downloaded but can't be decoded; legacy UID→figureId NVS map rewritten on every tap, consumed only by broken `deletefig`.

### 3.3 Audio (`src/AudioController.cpp`, 1362 lines)
- **C — Headphone jack is silent**: `DACPOWER=0x30` powers only LOUT1/ROUT1; the jack is on LOUT2/ROUT2 (never powered, volume never set); ROUT1 is unconnected. If the jack contact pulls AMP_CTRL low on insertion the device goes fully mute.
- **C — Amp enable (GPIO41/AMP_CTRL) is configured as INPUT and never driven**: speaker on/off is undefined, no mute between tracks, pops at codec power-up and sleep.
- **H — SD reads inside the decode thread** behind the FATFS lock; the 8 KB read buffer does not help because the decoder itself blocks.
- **H — NVS write on every volume step while holding the audio mutex** (hold-repeat = write every 100 ms).
- **H — 8 KB PSRAM leak per track start/resume/seek/beep** (buffer never freed) → ~1000 starts exhaust PSRAM; a docked device never sleeps so it eventually fails to play.
- **H — ES8388 VMID left disabled** (`0x00 = 0x04`); likely the source of the "distortion" fix comments. Port the Espressif ADF init sequence.
- **H — I2S driver installed/uninstalled on every start/stop/pause/track end** (clock lines stop under an unmuted codec; ~23 ms of audio discarded; internal heap churn).
- **H — Undebounced raw pogo read in the audio task stops playback** on a wobble while the NFC session stays active.
- **H — Possible MCLK signal-integrity issue**: BAT46 diode + 10 kΩ pull-up + 33 Ω into the codec; at 11.29 MHz the edge may reach only ~36–58 % of VDD. Scope it.
- M: audio task priority 1 (same as loop/SD writer); cross-task `String` races; pause/resume uses wall clock and a 96 kbps CBR byte estimate (ID3 tags shift it); volume beep can restart the playlist; no codec mute/amp-off before sleep; a failed track stops the whole playlist; double volume path (software gain + codec attenuation → quantisation noise at low volume); `APLL_AUTO` on a chip without APLL.

### 3.4 Connectivity (`src/ReverbClient.cpp` 921 lines, `src/WiFiProvisioning.cpp`, `src/ConfigManager.cpp`)
- **C — Anyone can command any device** (combined with backend §4): no `device_id` check, no auth, no rate limit; `set-max-volume 100` + `volset 100` removes the hearing-safety ceiling remotely; `reboot` inside the WS callback can be looped to drain the battery. Hub id = eFuse MAC, visible in every WiFi frame and in the BLE name.
- **C — All TLS unauthenticated** (`setInsecure()` everywhere, `CONFIG_ESP_TLS_INSECURE=y`, `SKIP_SERVER_CERT_VERIFY=y`); API over plain HTTP.
- **C — 1 Hz status report on a public channel** leaks home SSID, RSSI, battery, current track and the docked NFC UID; each frame becomes a Horizon job plus an echo. Frames silently dropped when the JSON exceeds 512 B (long track path).
- **H — Reverb/API never start if WiFi isn't up 5 s after boot**; no GOT_IP hook; a docked device stays offline until reboot.
- **H — `reverbstart` while connected leaks a live `WiFiClientSecure`** (~24 KB internal + a socket) — the leak `reverbclean` exists to paper over.
- **H — Blocking HTTPS POST to `/broadcasting/auth` inside the WS receive callback** at every (re)connect: second TLS session concurrent with the first (~60–70 KB internal at that moment).
- **H — Reconnect every 2 s with no backoff**: DNS + TCP + TLS on loopTask while the server is unreachable.
- **H — Owner-user token in plaintext NVS**, no NVS/flash encryption.
- M: strstr-based frame classification; `urlBuffer` clobbered after first connect (latent); WiFi drops invisible to the client (~33–51 s to notice); `handleBackgroundReconnection` blocks 5 s every 30 s and fights auto-reconnect; BLE memory not released after first-time provisioning until reboot; shared PoP `abcd1234`; `pusher:error`/`subscription_succeeded` ignored; the device→server `device-report` is not a valid Pusher client event (works only through the backend's listener and lets anyone spoof any device's status).

- **C — NFC callback does HTTP + SHA on loopTask** (see 3.1/3.2).
- **C — Boot blocks before buttons/NFC exist**: 30 s WiFi wait in `wifiProv.begin` + 5 s + 10 s Reverb + fixed delays; ~36 s out of WiFi range, paid on every button wake.
- **C — PN532 RF field likely left on for the whole session** (infinite passive-activation retries, no RF-off after read) → the "30–45 mA" attributed to the PN532.
- **H — One GPIO (4) switches all four rails** (4.5 V, SD, NFC reset, audio); nothing can be gated individually while awake; `poweroff` cuts SD/codec under live drivers.

### 3.6 Battery, charger, gauge
Hardware: BQ25792 charger (CE on GPIO44, 2 MΩ pull-up → charging is OFF unless firmware drives CE low), BQ28Z610 Impedance-Track gauge with FS8205A FET pair between cell and PACK, 2 mΩ sense resistor on the low side, CH224Q PD sink, two RT6160A (3.3 V always on; 4.5 V rail enabled by GPIO4), all on a **bit-banged** I2C bus on GPIO1/2 (both hardware I2C controllers are used by the codec and the PN532). Cell spec from `datasheets/batteryInfo.jpeg`: 4000 mAh LiFePO4, 3.65 V max, 0.2C recommended / 0.5C rapid / 1C max charge, 2.0 V cutoff, 25 mΩ AC resistance. `bq28z610.txt` is a duplicate of `sluua65.txt` (the TRM). The device's own `help` output lists commands (`gaugeocvfr`, `drainmark`, `sleepstep`, `pogowake`) that exist in **no commit**: the board runs an uncommitted tree (a42a68f-*dirty*).

**Why there is no golden image (verified against the TRM, `sluua65.txt`):**
- **C — The Chem ID is never programmed.** The firmware writes and reads word 0x0418 at DF **0x4628** (`BatteryManagement.cpp:1253`, `:1178`). The TRM's DF table has no 0x4628 (it goes 0x4626 → 0x4629 = Broadcast Pacing), so "Gauge Chem ID: 0x418" is a read-back of its own write, and the high byte sets Broadcast Pacing to 4 s. The real chemistry is read with MAC 0x0006 (TRM §12.2.6) and can only be *programmed* with bqStudio's Chemistry plugin (OCV/Ra tables), not by a DF word. The gauge is therefore still running TI's default 4.2 V Li-ion OCV table on an LFP cell, which is exactly what the telemetry shows (1 % at 3.25 V, 3 % at 3.47 V, FD/TD set). QMax learning is impossible with the wrong OCV table.
- **C — Charge termination can never be "valid".** The firmware writes 3600 mV to **0x468C/0x468E/0x4690** (`:1242-1244`) believing they are the charge voltages; those are the *Charging Voltage Low/Med/High range boundaries* used to select charging current (hence `ChargingStatus` shows PV at 3.47 V). The actual per-temperature charging voltages (0x4666 / 0x466E / 0x4676 / 0x467E) are untouched at 4000/4200/4000/4100 mV. Valid charge termination needs cell + Charge Term Voltage ≥ ChargingVoltage(), i.e. ≥ 4.0 V, which an LFP cell never reaches → VCT/FC never set, no end-of-charge QMax update, RSOC never 100 %.
- **C — No LFP overcharge backstop and CE asserted before VREG is verified.** Gauge COV is left at the Li-ion default 4300 mV; BQ25792 VREG POR is 4.2 V; `applyPowerConfiguration` asserts CE low regardless of whether the REG01 (3.6 V) write succeeded (`:539`, `:870`). A NACKed write after a charger POR = charging an LFP cell toward 4.2 V with nothing to stop it.
- **C — Current calibration is a single stale sample** of the charger's one-shot IBAT ADC (re-triggered every 5 s) at 300 mA against the gauge, with ±5–7.5 % charger accuracy (`:2267-2345`). Evidence it is off: charger in CC at 1000 mA with no DPM yet gauge read 767 mA (−23 %); RemCap rose 82 mAh in 140 s while Current() implies ~43 mAh (Capacity Gain vs CC Gain mismatch?). TI's procedure needs a known 1–2 A reference, CAL mode and averaging. A wrong gain copied into a golden image corrupts every unit.
- **C — The firmware prevents the rest at full charge.** The "kick" toggles EN_CHG every 10 s whenever the charger is not in a charging state, including *Charge Done* (`main.cpp:770-776`, `:593-600`), starting a fresh CC/CV pulse; VRECHG is left at POR 200 mV (recharge at 3.40 V, ≈ relaxed-full OCV of LFP). The 2 h relaxed-full OCV the learning cycle needs never happens.
- **H — The learning commands sabotage themselves:** `learndis` re-enables charging at its 2.90 V floor (above Term Voltage 2500 mV, so EDV/Ra at empty are never reached); `learnrest` sleeps with the ~13–33 mA pad-hold load so OCV is taken under load; `OCVFR=1` adds 48 h waits; `gaugeresetlearn`/`gaugelearned` issue DEVICE_RESET under load (clears VOK); `gaugelearned` claims to write 0x06 but writes 0x04.
- **H — Charger ITERM (POR 200 mA, trips 20–40 % higher) ≥ gauge Taper (200 mA)**, so the gauge's taper window never qualifies.
- **H — Non-idempotent MAC toggles (IT enable 0x0021, FET_EN 0x0022) fired every 5 s from unverified block reads** (no command echo, no checksum check; `:1418-1425`, `:2014-2021`). One bad read disables IT or drops FET control on battery.
- **H — Runtime telemetry depends on UNSEALED DF/MAC reads every second**; the gauge is in FULL ACCESS as shipped and is never sealed. Production cannot seal without breaking telemetry; any bus glitch can write DF.
- **H — SOC falls back to a voltage curve on any failed poll** (≈95 % at 3.47 V vs RSOC 3 %) — the "bar flashes full" glitch the LED code filters.
- **H — 2000 mA charge through a 1.0 mm-pitch single-contact connector** (`main.cpp:729-732`), vs 1 A in `FACTORY_BRINGUP.md`. Unreachable anyway (charger is in CV at 1.45 A) and heats the connector.
- **H — Residual corruption from earlier wrong writes is never checked:** eb3f4a8 wrote Term Voltage to 0x4632 (SOC Flag Config A), taper to 0x4692, "taper voltage" spilling into 0x4695 (Charge Term Voltage), 4200 to 0x4682. If 0x4632 lost FCSETVCT, FC can never be set. Protection Config reads 0x02 vs TI default 0x03.
- **H — GaugingStatus decoder mislabels bits** (bit 2 is TD not TC; bit 3 TC; bit 4 BAL_EN): the board's 0x11815 = VDQ, QEN, VOK, BAL_EN, TD, FD.
- M: bit-bang driver ignores clock-stretch timeouts (silent data corruption), no 9-clock bus recovery (a reset mid-read wedges the bus and then low-voltage cutoff never fires because it requires telemetry), keeps clocking after an address NACK; I2C Config 0x01 leaves BCAST enabled (gauge may become a bus master every 4 s now that pacing was corrupted); `battery.begin()` runs before GPIO4 is high so the RT6160 is configured with EN low on every boot and the "not ACKing" path reruns the 0.3 s reconfiguration every second; Temperature Enable 0x03 = max(die, TS1) with a fixed-divider TS on the charger (`TS_IGNORE=1`) → firmware is the only thermal gate and it's inactive during bring-up/learning/recovery; Design Voltage left at 7200 mV (2S default); FET Options 0x20 opens the CHG FET on TC; Term Voltage 2500 mV vs firmware cutoff 3.0 V loaded (user sees 2–5 % at shutdown); the VBUS-present path never sleeps.
- Correct as written: BQ25792 VSYSMIN/VREG/ICHG/IINDPM/VINDPM/cell-count/watchdog-off/ship-mode registers, RT6160 0x63 = 4.5 V, and the gauge DF addresses for gains, Term Voltage, FET/I2C/Power config, SOC flags, IT config, thresholds, design capacity/energy, QMax, Update Status, taper (0x4693) and protections. The MAC write protocol (block to 0x3E + checksum/length to 0x60/0x61) matches the TRM.

**The 100–185 mΩ cell→PACK drop (bench):** R163 is low-side so it is not in the BAT–PACK reading; Q1 is the high-side pair. "Resistance" falling as current rises fits a fixed ~95–100 mV offset (uncalibrated PACK ADC channel, TRM §11.3) plus ~35 mΩ of real FET/lead resistance. The charger in CV holds BATP at 3.600 V ±0.5 %, so true PACK is ~3.60 V, not 3.63. At taper (200 mA) the drop shrinks to ~20 mV, so the cell does reach ~3.58 V; the drop costs charge time and bakes connector/lead resistance into Ra, but it is **not** what blocks the golden image. Decisive test: DMM across Q1 S1–S2 and across CN33 pins 1–2 during a 1.5 A charge.

**Loop cost of this subsystem:** ~100 ms/s of busy-wait at 1 Hz (effective bus clock ~30–40 kHz because of `pinMode` per bit), ~370 ms once every 5 s (and every second while any device is not ACKing), `begin()` 1.07 s measured, `battery` command 370 ms measured. Worst case seconds if SCL is held.

**Verdict:** keep the power-flow logic (monitor phase, dead-cell hold, PD budget, wake stub, ship-mode cutoff) and the BQ25792 register knowledge; rewrite the gauge layer (golden image instead of scattered DF writes, sealed-mode standard commands at runtime, verified MAC reads, no toggles from unverified state) and the I2C transport (own task, open-drain register-level GPIO, stretch handling, bus recovery). Fix the charger supervisor in place (no kick at Done, ITERM 80–120 mA, VRECHG 300–400 mV, 1 A, CE gated on a verified VREG, COV 3750 mV).

**Bench procedure to produce a golden image (needs EV2400 + bqStudio for the chemistry):**
0. Firmware prep: a `battquiet` mode (configure charger once, CE held low, all battery-bus polling stopped so the EV2400 can share the bus); remove the done-state kick; ITERM 120 mA; VRECHG 300–400 mV; ICHG 1 A; `learndis` stays in HIZ at its floor and the floor = Term Voltage.
1. Chemistry: run TI GPCCHEM on this cell (C/10 discharge with relaxation logging), program the returned LFP Chem ID with bqStudio's Chemistry plugin, confirm with MAC 0x0006.
2. Data flash via bqStudio: Design 4000 mAh / 1280 cWh / Design Voltage 3200 mV; DA Config 0x18; Low/Standard/Rec/High-Temp Charging Voltage = 3600 (0x4666/0x466E/0x467E/0x4676); voltage ranges Precharge/Low/Med/High = 2500/2900/3300/3450; Taper 250 mA; Charge Term Voltage (0x4695) 100 mV; Dsg/Chg/Quit 100/75/40 mA; Term Voltage 3000 mV; COV 3750/3550; CUV 2500/3000; I2C Config 0x00 and Broadcast Pacing restored to 15; FET Options 0x00; IT Gauging Config 0x14C6 (OCVFR=0) for the bench; Temperature Enable 0x02 if a pack NTC exists; repair 0x4632 = 0x0C8C, 0x4692 = 0, 0x4682 = default.
3. Calibration with a 0.1 % DMM and a known 1–2 A source per TRM §11.4.3 (CC offset, board offset, CC gain, capacity gain, cell/BAT/PACK voltage, TS1).
4. Learning cycle at 20–30 °C: discharge at ~C/5 to Term Voltage, rest 5 h at <10 mA; IT Enable (0x0021), confirm QEN/REST/VOK; charge at ~0.5C, confirm VCT/FC, rest 2 h with no kick/recharge → expect Update Status 0x05; discharge at C/5 to Term Voltage (Ra update), rest 5 h → expect 0x06, QMax within ±5 % of 4000, Ra flags updated.
5. Image: restore OCVFR=1, reset Cycle Count/lifetimes (0x0028), export Golden Image (`.srec` + `.df.fs`) from bqStudio.

**Production flow:** embed the `.df.fs` in the ESP firmware and replay it over the bit-bang bus with polling stopped (ROM mode at 0x0B; suspend the fallback probe); verify Chem ID (0x0006) and Update Status; per-unit CC calibration on a fixture with a reference current (never the BQ25792 IBAT); enable IT if exported disabled; seal with custom keys (0x0030/0x0035); runtime firmware uses only sealed-mode standard commands.

## 4. Backend findings (`portal.tilkietalkie.com`)

**Critical / blocking for any production rollout or OTA:**
1. **`GET /api/hubs/{uuid}/token` has no auth** (BE `routes/api.php:24`, `Api/HubController.php:87-122`). uuid = eFuse MAC decimal (also the BLE name). Returns a never-expiring, unscoped Sanctum token for the hub's **owner user**, and deletes the previous one (knocks the real device offline; a user with two hubs has them revoke each other on every boot).
2. **Device channels are public** (`new Channel('device.…')` in all three events); the admin page sends commands from the browser as client events and `DeviceCommandListener` re-broadcasts any `device-command` from any socket. Anyone with the public Reverb key (in the JS bundle, equal to the literal in firmware) can control, reboot or surveil any device. `allowed_origins: ['*']`. Private-channel callback has an `X-Client-Source: esp32` bypass; `App.Models.User.{id}` casts to int so any Firebase user authorizes any other's channel.
3. **Reflected XSS / Firebase oobCode exfiltration** via `/auth/email-link?appScheme=…` (`web.php:42-44`).
4. **`.env.production`: `APP_DEBUG=true`, `LOG_LEVEL=debug`, `DB_CONNECTION=sqlite`** with Horizon (10–15 workers) + Reverb + web + Sanctum `last_used_at` writes on every device request → "database is locked"; `QUEUE_CONNECTION` defined twice; Debugbar enabled whenever debug is on.
5. **Horizon gate = `test@example.com`** with open web registration.
6. **IDOR**: `GET /api/units/{nfc_id}` has no ownership check since 9fdaca9 → any user (including via the open legacy `/api/register`) gets any unit's manifest, including other families' custom recordings; `bind/unbindContentFromUnit` likewise.
7. **`users.id` is a string but every FK is bigint** (works only on SQLite); strict `!==` comparisons break legacy numeric-id users; `User::updateOrCreateUser` re-keys an existing user to a new Firebase UID by email without checking `email_verified` (account takeover if the Firebase project allows unverified sign-ups).
8. Chat event broadcasts the full `User` model (email, google_id, shopify id) on the public channel.

**Contract state (IDF-Migration firmware vs backend):** the firmware does parse the current manifest (`contents[]`, `custom_tracks[]`, `asset_manifest[]`, `storage_path`, `checksum`, `file_size`), caches it on SD per unit, and stores assets at `/assets/contents/<content>/<episode>/<track>.mp3`. **OTA/factory readiness:** nothing exists (confirmed). Prerequisite is device identity (Hub gets `HasApiTokens`, device-scoped abilities, private channels, server-side command publishing). Proposed tables: `firmware_releases` (device_id, hardware_rev, version, version_code, channel, file_path on a private disk, size, sha256/md5, min_version_code, rollout_percent, mandatory, revoked_at), hub columns (hardware_rev, mac, firmware_version/_code, channel, pinned/target release, ota_status/error, last_seen_at, provisioned_at, qa_passed_at), `hub_firmware_events`, `hub_factory_tests`; device API `GET /api/device/firmware/check` (204 / 200 + signed 15-min download URL, ETag/304), signed `download`, `POST status`; admin Firmware pages with image validation (0xE9 magic, `esp_app_desc_t` at 0x20, version at 0x30) and rollout slider; factory `POST /api/factory/hubs` (idempotent upsert, returns the hub token once) and `/qa`.

## 5. Hardware observations (for the board owner)

1. **Cell→PACK path ≈ 100–185 mΩ** (gauge BAT vs PACK at 0.77–1.45 A). Charger CV/taper is reached at the PACK node while the cell is 120–150 mV lower: slower charge, early taper, and it undermines the gauge's full-charge detection and learning. Candidates: FS8205A Rds(on) at the gauge's gate drive, the 1.0 mm-pitch cell connector (CN33), traces, and the 2 mΩ sense resistor placement. Measure cell-terminal vs PACK with a DMM at a known current to apportion.
2. **Gauge temperature is constant 30.1 °C** across samples → TS1 network (R165/R166/C149) looks like fixed resistors, i.e. no thermistor; the gauge then has no real temperature for Impedance Track.
3. **One GPIO (4) gates 4.5 V, SD, audio and NFC reset** through 1N5819 diodes; individual gating is impossible. Respin: separate enables.
4. **Headphone jack wired to LOUT2/ROUT2** (never powered by firmware); ROUT1 unconnected; speaker gets the left channel only.
5. **AMP_CTRL (GPIO41) shared with the jack detect contact**; firmware leaves it as input. Confirm what holds NS4150B CTRL high with no plug and whether GPIO41 may drive it low.
6. **MCLK through BAT46 + 10 kΩ pull-up + 33 Ω**: marginal edges at 11.29 MHz; scope at ES8388 pin 1.
7. **SD pull-ups (10 k) to always-on 3.3 V while SD VDD is switched**: back-powers the card in sleep.
8. **Button RC (390 Ω + 100 nF) referenced to +3.3 V instead of GND**; verify for phantom presses on rail steps.
9. **No pull-down on REED_SW_MC on the main board** (only on the top PCB); floats if the top PCB is unplugged while armed as a wake source.
10. **Charger CE on U0RXD (GPIO44)**: charging depends on firmware running; a crash loop on USB stops charging. QON not wired, so ship-mode exit is USB-only.
11. **LED data at 3.3 V into a WS2812 on 4.5 V** (V_IH 3.15 V): marginal.
12. **No NTC on BQ25792 TS** (fixed divider), `pdvolt 20` can request 20 V on VBUS — check cap/LED ratings.
